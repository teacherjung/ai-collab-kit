# ai-collab-kit

一套可以搬到任何專案的「一個人＋兩個以上 AI」協作架構。

## 目的（每一條規矩、每一道閘、每一題考題都以它為方針）

擁有者 2026-09-13 定的：**建立一個組織架構，讓他未來能夠順暢地調度 AI（軍隊），來實現他想製作的專案。**

換成可以拿來判斷的話：他是指揮官，AI 是部隊；架構的目的是**他下令、部隊可靠地做出來、他不必逐一盯**。「順暢」指的是**他的**摩擦最小——讀得少、裁得少、不用記程序。閘與考題的價值是讓他不必自己檢查就能信任結果，不是為了防誰使壞。可搬性是為了同一套編制能派到任何新專案。

所以一條規矩、一道閘、一題考題進來之前，多問一句：**這讓他調度更順、還是只是另一道疤？** 只因為過去某次事故而存在、但不讓調度更順的東西，是候選刪除對象。

從 personal-finance-webapp 兩個月、六百多支 PR 的經驗重建。**不是搬過來，是從零重寫**：一條規矩要進來，必須帶著它的理由和它的執行者。原專案的協作規矩四份加起來約 13 萬 5 千字（規則正本那一份約 9 萬 6 千字；這是**字元**數，不是位元組——本檔原本寫「19 萬字」是把位元組當字數，2026-09-13 量過改正），根本原因是規矩本文、事故沿革、邊界說明三種東西攪在同一份文件裡；這裡把它們分成三層。

## 三層

- `RULES.md`：**本文**（**產物，不要手改**：規矩住在 `rules.json`，一則一筆；改完跑 `node tools/build-rules.js` 重新產生。考題會比對兩者逐字元相同）。**規矩正文**的上限見本文 K2；哪些字算、哪些不算只寫在 `MACHINES.md` 的 K2 那一列。只放背得起來、天天要用的規矩；新條要先過下面「進門規則」的進門五問。版面約定（條號、角色名、關鍵詞、灰底框怎麼排）與每個關鍵詞的意思在 `GLOSSARY.md`（用語對照表；不算字數，跟本文一起搬）。每條規矩「為什麼存在」的一行摘要在 `cases/DIGEST.md`（由案例簿產生、不要手改；擁有者 2026-10-07 裁：跟用語對照表同待遇——不算字數、跟本文一起搬，不帶案例簿的專案也帶這一份）。

  條號＝**英文字母＋數字**（`A1`、`B2`…）：字母是小節、數字是該節裡的第幾條。原本用天干（甲乙丙…）只有十個、不夠擴充，裁示者 2026-09-12 裁改成字母，A 到 Z 共二十六節。新增小節就往後接一個字母；小節內新增就接下一個數字。已經用掉的條號原則上不回收再指別條，案例簿與範本都靠條號指回來。第二輪（裁示者 2026-09-26 定案）是例外：舊 C1、C2 併成新 C1、舊 C3 遞補成 C2，舊 E9 拆成 E9、E10；同一支PR把指錯條號的案例一起改。案例簿考題擋得到「條號不存在」與「有條規矩沒案例指著」，擋不到「條號還在、意思換了」，那一半靠自覺。
- `cases/`：**案例簿**（索引 `cases/README.md` 與摘要 `cases/DIGEST.md` 是**產物**：由案例檔、`cases/index.json`（摘要另讀 `rules.json`）算出來，改完跑 `node tools/build-casebook-index.js`）。每一條規矩為什麼存在：哪一次事故、哪一天、代價多少，或哪一則可靠的外部經驗（算法在下面「進門規則」第一問）。一則一檔、檔名英文、每則指回本文的一條。⚠️ 進公開倉庫前要先去掉任何個人狀況。
- `settings.json` → `PROJECT-SETTINGS.md`：**專案設定**。值只有一份（`settings.json`），人讀的那份是產物；每個專案搬進去後逐欄填。套件倉庫根目錄那一份填的是**套件倉庫自己的值**（2026-09-26 起，讓合併指令在套件倉庫跑得起來）；給新專案的空白範本＝`tests/helpers/unfilled-settings.json`。
- `tools/`、`templates/`、`tests/`：**機器**。守得住的規矩寫成腳本、考題、範本。本文只寫「這條有機器守」，不重述機器做什麼。

## 搬進一個專案

照順序做；每一步後面寫的是「漏了會怎樣」。第一個真專案（personal-finance-webapp）2026-09-15 起在它的雲端三關全綠（`tests/placement.test.js` 檔頭有記）、2026-09-17 起它的協作規矩正本改為套件本文（它的 AGENTS.md 有記）；本倉庫 2026-09-26 起也用同一套管自己。步驟仍是修到哪補到哪。

1. 從套件的一個**固定版本**取檔（`git archive <版本> <路徑…>`，不要整個資料夾照抄）：`tools/`、`tests/`、`templates/`，加上根目錄的 `rules.json`、`RULES.md`、`MACHINES.md`（工具與考題從根目錄讀它們）、`GLOSSARY.md`（用語對照表：本文的版面約定與關鍵詞，本文檔頭指著它）、`docs/money-guard-two-pattern-tables.md`（禁區攔截器「兩張樣式表」的正本；`tests/forbidden-tools.test.js` 的 ⑭ 釘著它在不在——只搬這一個檔、不搬整個 docs/）、`cases/DIGEST.md`（每條規矩為什麼的摘要；不帶案例簿的專案也帶這一份——只有它的 `cases/` 不算帶了案例簿）；`settings.json` **不要從根目錄取**——套件倉庫根目錄那份是套件倉庫自己的值（平台、倉庫身分、參與者、合併指令都指向套件倉庫），要從空白範本取：`git show <版本>:tests/helpers/unfilled-settings.json > settings.json`，逐欄填完再跑 `node tools/build-settings.js` 產生 `PROJECT-SETTINGS.md`（這一份也不要從根目錄取）。空白範本的 `forbidden` 那一塊**帶預設名單**（裁示者 2026-09-26／27：同一個連接器不用每個專案都填一遍、禁區不管哪個專案都要一樣）：碰錢連接器與白名單（所有碰錢連接器共用一份：唯讀查詢＋提醒／觀察清單＋回饋一支）、拒絕清單（兩支下單工具＋測試鈕）、不碰錢的連接器、家族網詞表、兩張樣式表，抄了就有；`tests/forbidden-defaults.test.js` 要求專案擋的方向那六個清單（`servers`、`deny`、`verbs`、`nouns`、兩張樣式表）至少包含它（少一項就紅；可以多加、不可以少）；放行方向的欄位（`safeServers`、`allowedTools`、`allowlist`、`readPrefixes`）不比；逐工具登記 `allowedTools` 預設為空，欄位分工與來源要求見正本「兩張樣式表」；任何一欄多加一項這一題都不比（放行方向多加、`servers` 多登記一個連接器都可能更鬆），那是改禁區清單本身，照第 3 步的手續；同一支考題也釘住範本自己的筆數與正本「預設字彙表」的表格（範本縮水、正本改了範本沒跟上都紅）。⚠️ 連接器登記名是**這個 claude.ai 帳號**的連接器編號（桌面內建與 Codex 的用名字）——換帳號＝編號不同，把新帳號的編號**補進** `servers`／`safeServers`（碰錢那一欄的舊編號留著：考題要求至少包含範本，舊編號在新帳號永遠比不到、留著無害，要拿掉先改套件範本；不碰錢那一欄的舊編號可以拿掉；拒絕清單那兩支下單工具的名字也綁著舊編號，要照新編號補一份）（並照第 3 步重印釘指紋那一行、補複本、重按信任）；預設字彙表加了哪些字、刻意不加的字與代價、守不到的＝正本「兩張樣式表」那一份裡「預設字彙表」那一節。抄錯了會紅：`tests/settings.test.js` 有一題比對設定裡的倉庫身分跟這棵樹的 origin 遠端，指向別的倉庫就擋下；`cases/` 在不在對不上就紅（`tests/casebook.test.js`）；不帶的專案裡案例簿那五題顯示跳過並寫出原因。不帶案例簿的專案沒有「本文每一條都有案例指著」這道檢查，所以規矩本文只在套件那邊改、再同步過去（D5）。**不要帶** `~/.local/share/ai-collab-kit/guard/<指紋>`：樹裡的清單怎麼改都沒有用；這台機器沒有那一行要的那一份複本、或複本裡多了東西＝所有 mcp__ 工具全擋（看得見）。順序（完整手續在 `tools/guard-copy.js` 檔頭「Claude 側釘指紋裝法」，這裡是節錄；⓪同下——清單上要先有測試鈕）：①先補複本——`git fetch`，在專案裡跑 輸入被放行、照清單該擋的假名印出拒絕、改過一個位元組的副本退 2），過了才落地；落地之後再用你的家目錄（會讀你的登入設定）跑一次，沒過就撤掉這一次落地的那一份、退 1——Claude 起鉤子是不是登入 shell 沒量，登入設定往標準輸出印字會把拒絕弄成放行。落地之後、這一次試跑跑完之前把它中斷＝那一份留著，下一次再跑走「已經在」那條路：試跑過＝退 0；沒過＝退    - **核過原文**：有人讀過原文裡撐這條規矩的那一句，只看別人的整理不算。那一則的來源欄附原文連結；連結或出處帶 AI 產品、公司名（案例簿不收這些名字）時，連結與核過的那一句改記在落地那支 PR 的說明，來源欄指到那支 PR。
   - **我們也會遇到**：寫得出為什麼我們的情況跟他們一樣。
2. **執行者**：哪支腳本、考題或閘在守它；沒有就老實標「靠自覺」。標籤名字的定義在 `MACHINES.md`。
3. **通用**：不綁任何專案的檔名、人名、工具名。
4. **更順**：擁有者的原話——「在不失去品質的前提底下，時間耗費盡可能低、Token 消耗也盡可能地低。但不為了省時、省 Token 而對安全、品質打折」。白話：說得出它讓擁有者調度 AI 哪裡更順（少讀、少裁、少記、或不必自己檢查），而且不是拿安全或品質去換；說不出來就算有案例也不進。
5. **白話**：擁有者讀一遍就懂；用到的關鍵詞在 `GLOSSARY.md` 查得到。

## 本倉庫自己怎麼合併

- **複審結論**：可由複審者自己貼成 PR 底下的一般留言（`gh pr comment`；不要用 `gh pr review`——結論聯集閘只讀 PR 的一般留言），或輸出純文字結論至本輪 `outFile`（文末可單獨寫「未貼」）後由外殼跑 `node tools/review-launch.js --post <編號> [--file <結論檔>]` 核過兩棵樹與標頭再代貼；第一行照 `templates/verdict-header.md` 逐字，來源字串照 `PROJECT-SETTINGS.md` 第二節（F4、F5）；「通過」那一則還要有兩個固定小標（F7）。走「快速通道（擁有者）」的，**擁有者** 就是複審者：他說「通過」後，實作者把他的原話逐字貼成結論留言，第一行照範本、不用兩個固定小標（F12；結論閘認專案設定登記的擁有者）；走「快速通道（AI）」的照一般的結論格式。

  2. 複製印出的啟動指令執行掃描，將輸出寫入 `output.log`（第一行標頭 `🔍 <識別值>｜來源：<來源字串>｜掃 \`<受審版本短碼>\``，全文禁含複審機器人記號 `🤖`，且不可自行填寫 `掃描時序`），再跑 `node tools/review-launch.js --scan-post <編號> [--file <輸出檔>]`（自訂暫存父目錄時加 `--dir <目錄>`；不給 `--file` 時預設讀 `scan.json` 的 `outFile`）：外殼核驗掃描樹乾淨與 HEAD 未變（不符退 1）、全文無 `🤖` 且無自填時序、第一行 `🔍` 標頭相符、平台版本未變且當版尚未貼過掃描留言，自動在標頭後補上權威時序行 `> 掃描時序：依據複審留言 <連結>｜準備 <時間>｜代貼 <時間>｜範圍 \`<基底短碼>..<版本短碼>\`` 並呼叫 `reviewLaunch.postComment` 代貼成 PR 留言。
