# 人工預約表會過期，改成開工先開草稿PR

- 日期：2026-07-31
- 本文條號：D3、E1
- 發生什麼：7/24 定下的協作框架裡，開工前要在一張人工預約表登記誰在改哪些共享檔案、合併後釋放。7/31 平常當複審者的另一方 AI 做了一次文件唯讀盤點，指出專案進度文件只提到一支 PR、實際開著五支，而且一份文件寫預約已改走草稿PR、規則那份還指定預約表，建議以草稿PR 當唯一即時來源、不再人工維護第二張表。裁示者回「如果你也認同，就讓預約表退役。如果你不認同就保留。我想聽你的意見。」；實作者認同，另加一道「開工第一步＝先開 Draft PR」（不然開工到第一次推送之間沒人知道你在做什麼），他回「全部聽你的建議，開工吧。」。落地那一支第一輪複審指出 PR 上只看得到已提交的檔案、蓋不住預計範圍，實作者才補「PR 說明開工時列出預計修改的共享檔案／區域」，並自己標明這是對裁示的補洞、不是他的話。9/24 他問起 D3 當初為什麼要先開草稿，印象中是因為 GitHub 上出現很多錯誤提醒；實作者查到理由只留在理財網頁那顆提交、案例簿沒有，他裁補這一則；同一天欄名也改成「預計修改的檔案」，不再只列共享的。
- 代價：表形式上在、實際上過期：7/29 下午到 7/30 晚上同時開著五支 PR、表上只寫一支，而且那一支早已合併；7/31 盤點時表上一支都沒登記，誰在改哪些檔案查不準。理由後來只留在提交紀錄，9/24 裁示者問起時印象中是另一個原因，要實作者回頭翻提交才查到。
- 教訓：「誰在做什麼」交給會自己更新的東西（開著的草稿PR），不另維護人工表；PR 上只看得到已提交的檔案，所以開工就在說明寫出預計要改的；定下規矩的當下就把理由寫進案例簿，別只留在提交訊息。
